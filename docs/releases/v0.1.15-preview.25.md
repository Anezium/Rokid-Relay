# Rokid Relay v0.1.15-preview.25

Release type: preview fix
Date: 2026-07-07

## Highlights

- The self-arm Wireless Debugging bootstrap now updates the glasses helper **before** it starts. Previously, tapping Bootstrap with an outdated helper on the glasses silently ran the whole flow against the old helper: the on-glasses `127.0.0.1` self-pairing from preview.23 never engaged, the phone fell back to the legacy same-network pairing, and users kept hitting the exact "Phone and glasses must be on the same Wi-Fi" error that preview.23 was built to eliminate — indefinitely, because nothing ever triggered the deferred helper update.
- Tapping **Bootstrap** now installs and starts the bundled glasses helper first whenever it is newer than the installed one, with visible progress ("Updating glasses helper…"), and only then asks the glasses to set up Wireless Debugging.
- If the helper update fails, the app now says so explicitly ("Glasses helper update failed: …") instead of proceeding into a doomed pairing attempt. Pairing codes reported by a stale pre-update pairing dialog are ignored while an update is pending, so the legacy LAN path can no longer start behind an update's back.
- Ordinary relay usage is unchanged: helper updates outside an explicit Bootstrap request keep the existing non-disruptive deferral.

## Root cause

- `ClientBootstrap` defers bundled-helper installs until a foreground launch but still reports the message link as ready. The wireless-setup request path trusted that readiness and messaged whatever helper was installed. An old helper reads the pairing code and hands it to the phone without ever announcing `self_pairing_started`, which is precisely the signal the phone uses to hold back its legacy LAN bootstrap — so the fallback engaged every time.
- Field evidence: a user's "Last activity" showed `Glasses app: glasses helper update pending` alongside the recurring same-Wi-Fi failure; both screenshots of the failing bootstrap carried that pending-update state.

## Verification

- Reproduced the field scenario on real hardware (phone remembering the old helper fingerprint, old helper on the glasses, wireless bootstrap not armed): tapping Bootstrap installed the bundled helper (~12 s over the CXR link), started it, and only then sent the setup request. The updated helper ran the automator to the pairing dialog, self-paired over `127.0.0.1` in ~3 s, the phone logged `phone LAN bootstrap suppressed while glasses self-pairing is in flight`, and `WRITE_SECURE_SETTINGS` ended `granted=true` on the glasses.
- Forced a helper-install failure (phone Wi-Fi radio off, which starves the CXR file transfer): the Self-arm row surfaced "Glasses helper update failed: glasses install failed" and no legacy LAN attempt ran. A later Bootstrap tap retried cleanly.
- Phone unit tests pass; both APKs build.

## Test Focus

- On a phone that upgraded from an older release (so the bundled helper is newer than the installed one): tap **Bootstrap** and confirm the status walks through "Updating glasses helper…" before the Wireless Debugging steps, and that the run ends "complete" without any same-Wi-Fi error.
- Keep the phone's Wi-Fi radio **on** during the first Bootstrap after an app update — the helper APK travels to the glasses over the CXR link's Wi-Fi transport. If the update fails, the row now says so; toggle Wi-Fi on and tap Bootstrap again.
